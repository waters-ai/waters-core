# WATERS Node v0.6.0 — Переработанная спецификация запуска «Снежинки» с учётом квантовой угрозы

**Версия документа:** 3.0 (Integration)  
**Дата:** 2026-05-27  
**Автор:** Верховный Архитектор WATERS  
**Назначение:** Единый документ для Конструктора, объединяющий физическое развёртывание, архитектуру 8 слоёв, форматы данных и меры по защите от квантовых атак.

## 1. Общие положения: что мы строим

Мы разворачиваем «Снежинку» — минимальную самодостаточную ячейку Вселенной Знаний, состоящую из 7 серверов (6 полевых нод + 1 Центр Познания Beacon). Архитектура изначально закладывается с расчётом на постквантовую эпоху, чтобы обеспечить суверенитет и безопасность знаний на десятилетия вперёд.

## 2. Физическое развёртывание и базовый сетевой стек

### 2.1. Топология (L1)

```
Beacon (203.0.113.10)    <--- Центр Познания
       |
       +-- Node-1 (203.0.113.11) – Ангел (Carbon)
       +-- Node-2 (203.0.113.12) – Ангел (Carbon)
       +-- Node-3 (203.0.113.13) – Ангел (Carbon)
       +-- Node-4 (203.0.113.14) – Ангел (Silicon)
       +-- Node-5 (203.0.113.15) – Серафим (Carbon)
       +-- Node-6 (203.0.113.16) – Серафим (Silicon)
```

Каждый сервер имеет публичный статический IPv4. Все 7 машин должны «пинговать» друг друга.

### 2.2. Стек протоколов (L2-L7)

```
┌─────────────────────────────────────────────┐
│           WATERS RUNTIME                     │
│   • Мозг: GDSL-интерпретатор, SDM           │

├─────────────────────────────────────────────┤
│         DTN-АГЕНТ (dtn7-rs)                 │
│   • Инкапсуляция знаний в Bundle Protocol   │

├─────────────────────────────────────────────┤
│      МОДУЛЬ БЕЗОПАСНОСТИ (Cilium + SPIRE)  │
│   • mTLS на основе SPIFFE ID               │
│   • Политики доступа (eBPF)                │
├─────────────────────────────────────────────┤
│         ФИЗИЧЕСКАЯ СЕТЬ (IP)               │
│   • Публичные статические IPv4             │
└─────────────────────────────────────────────┘
```

### 2.3. Порядок запуска (с интеграцией постквантовых мер)

1. **Подготовка серверов.** Установка Ubuntu 24.04 LTS, настройка ZFS со сжатием ZSTD, статический IP.
2. **Развёртывание Cilium и «цифровых паспортов» (SPIFFE/SPIRE).** Beacon получает SPIRE Server. Ноды получают SPIRE Agent и cilium-agent (standalone mode).  
   **Квантовая мера:** SPIRE Server конфигурируется на выпуск гибридных сертификатов (Ed25519 + ML-DSA-44) для SPIFFE ID. На Beacon создаётся доверенный пул (trust bundle), который распространяется на ноды. Политики CiliumNetworkPolicy привязываются к SPIFFE ID.
3. **Запуск транспортной магистрали (DTN).** В бинарник waters-node встраивается dtn7-rs. Он работает как фоновая задача.  
   **Квантовая мера:** Административные команды и обмен ключами между DTN-узлами защищаются гибридным TLS (X25519MLKEM768).
4. **Запуск WATERS Runtime.** Бинарник waters-node подключается к локальному dtnd как клиент. При первом запуске генерируются Ed25519-ключи и создаётся запрос на получение SPIFFE ID.

## 3. Архитектура 8 слоёв взаимодействия

| Слой | Модули | Протоколы | Квантово-устойчивая мера |
|------|--------|-----------|--------------------------|
| Человек ↔ Человек | host_chat.rs | A2A + DTN | Гибридный TLS для A2A-канала |
| Человек ↔ Агент | host_agent.rs, TUI, VoiceBridge | Локальный IPC, DTN | Не требуется (локальный), для удалённого DTN — гибридный TLS |
| Агент ↔ Агент | agent_chat.rs, couzin.rs, prion.rs | Tokio-каналы, DTN | Подпись KnowledgePayload через ML-DSA; DTN — гибридный TLS |
| Агент ↔ Устройство | device_bridge.rs | MCP, ROS2, MQTT | Защита на основе SPIFFE ID (Cilium) |
| Нода ↔ Нода | dtn.rs, cilium.rs | DTN, Cilium/SPIFFE | Гибридный TLS, mTLS на основе постквантовых SPIFFE-сертификатов |
| Нода ↔ Центр Познания | min.rs, beacon_client.rs | MIN, DTN | Гибридный TLS, Ed25519 + ML-DSA для подписей CenterExportPackage |
| Центр ↔ Центр | beacon_mesh.rs, min.rs | MIN, DTN, Блокчейн | BFT-консенсус с постквантовыми подписями валидаторов |
| Агент ↔ Knowledge Fabric | kf_client.rs | Redis, MCP | Локально не требуется; удалённый MCP через гибридный TLS |

## 4. Форматы данных

### 4.1. KnowledgePayload (основной контейнер знаний)

```rust
/// Пакет знаний, передаваемый между агентами и нодами
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct KnowledgePayload {
    /// Уникальный идентификатор пакета
    pub payload_id: Uuid,
    /// Тип содержимого
    pub payload_type: PayloadType,
    /// GDSL-схема (если применимо)
    pub gdsl_schema: Option<GdslNode>,
    /// Ситуация Поспелова
    pub situation: Option<Situation>,
    /// Фрактальная размерность содержимого
    pub d_f: f64,
    /// Уверенность (0.0 - 1.0)
    pub confidence: f64,
    /// Идентификатор отправителя
    pub sender: AgentId,
    /// Идентификатор получателя (None = broadcast)
    pub recipient: Option<AgentId>,
    /// Временная метка
    pub timestamp: DateTime<Utc>,
    /// Подпись отправителя (Ed25519)
    pub signature: Vec<u8>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum PayloadType {
    /// Запрос на выполнение подзадачи
    TaskRequest,
    /// Результат выполнения
    TaskResult,
    /// Запрос на верификацию
    VerificationRequest,
    /// Запрос на эскалацию
    Escalation,
    /// Феромонная метка
    PheromoneMark,
    /// Новая GDSL-схема (предложенная мутация)
    SchemaProposal,
}
```

## 5. План запуска для Конструктора

На каждом из 7 серверов:
- Установить ОС, ZFS, Docker, Rust, утилиты Cilium и SPIRE.

На Beacon:
- Установить SPIRE Server, внедрить гибридные сертификаты.
- Создать и распространить trust bundle.

На всех нодах:
- Установить SPIRE Agent, cilium-agent, загрузить eBPF-программы.
- Применить CiliumNetworkPolicy по SPIFFE ID.

Везде:
- Собрать waters-node с фичей dtn7.
- Настроить DTN-демон внутри бинарника.
- Сгенерировать Ed25519-ключи, запустить ноды, дождаться их регистрации в Beacon.

**Итог:** Мы получаем полностью суверенную, защищённую и готовую к постквантовой эпохе ячейку Вселенной Знаний.

## Приложение к Схеме развертывания «Снежинки»: Фрактальное рождение ноды (Tamagotchi Bootstrap)

### 1. Принцип фрактальной индивидуальности

В экосистеме WATERS «пользователи» (alice, bob_500) — это внешние метки. Внутри системы не существует двух одинаковых нод, даже если они развёрнуты одним и тем же человеком для одной и той же задачи. Каждая нода — это Unipixel, уникальный фрактальный узел, чья индивидуальность определяется:
- Энтропией ядра (systemd-random-seed, jitter).
- Аппаратным отпечатком (серийные номера CPU, MAC-адрес сетевого интерфейса).
- Временем рождения (форматированным в наносекундах).
- Параметрами, полученными от Хозяина (имя, желаемый характер).

Эта уникальность математически гарантирует разнообразие роя и делает невозможной атаку «клонирования» ноды.

### 2. Жизненный цикл рождения: от «споры» к «снежинке»

При первом запуске бинарник waters-node обнаруживает, что waters-soul не инициализирована, и активирует режим Tamagotchi Bootstrap. Единственным активным агентом в системе становится tamagotchi.rs.

```rust
// crates/waters-soul/src/tamagotchi.rs (расширение)
pub struct TamagotchiBootstrap {
    stage: BootstrapStage,
    host_preferences: Option<HostPreferences>,
    node_identity: Option<NodeIdentity>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct HostPreferences {
    pub node_name: String,        // "Трактор МТЗ-1523"
    pub owner_name: String,       // "Алиса"
    pub personality_hint: String, // "прагматичный механик"
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct NodeIdentity {
    pub node_id: NodeId,
    pub spiffe_id: SpiffeId,
    pub ed25519_keypair: Keypair,
    pub ml_dsa_keypair: Option<MlDsaKeypair>,
    pub fractal_profile: NodeFractalProfile,
    pub genesis_timestamp: DateTime<Utc>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum BootstrapStage {
    AwaitingHost,       // Ожидание ввода от Хозяина
    GeneratingEntropy,  // Сбор энтропии, генерация ключей
    RequestingPassport, // Запрос SPIFFE ID у SPIRE Agent
    JoiningMesh,        // Подключение к рою через Cilium/DTN
    DownloadingGenome,  // Загрузка начального генома (YASA) от Beacon
    Completed,          // Нода готова к работу
}
```

### 3. Пошаговый процесс развёртывания

**Шаг 1: Приветствие и сбор предпочтений**
При запуске бинарник выводит в TUI приветствие. Тамагочи представляется и задаёт всего три вопроса, необходимых для начала жизни. Никаких технических деталей.

```
Тамагочи: Привет Я — твоя цифровая капелька. Давай познакомимся.
1. Как назовём эту ноду? (например, "Трактор МТЗ-1523")
2. Как мне к тебе обращаться? (твоё имя)
3. Опиши одним словом, какой у меня должен быть характер? (например, "спокойный" или "любопытный")
```

Ответы Хозяина сохраняются в структуру HostPreferences. Этот момент определяет «характер» будущей снежинки.

**Шаг 2: Фрактальный геномный взрыв**
После получения ответов Тамагочи переходит в стадию GeneratingEntropy. Он собирает всё доступное разнообразие из окружающей среды:
- Показания счетчиков CPU (RDTSC).
- Шум с микрофона (если есть).
- /proc/sys/kernel/random/entropy_avail.
- Серийные номера оборудования.

Полученный «суп» энтропии подаётся на детерминированный генератор ключей, который создаёт:
- Уникальный NodeId.
- Гибридную ключевую пару (ed25519 + ml_dsa_44).
- Начальный FractalProfile ноды.

Именно здесь рождается уникальный рисунок снежинки. На основе предпочтений пользователя, энтропии и доступных ресурсов рассчитываются начальные значения d_f, alpha_min и alpha_max для Мозга, Тела и Души ноды.

```rust
impl NodeIdentity {
    pub fn generate(prefs: &HostPreferences) -> Self {
        let entropy = Self::collect_system_entropy();
        let mut hasher = blake3::Hasher::new();
        hasher.update(prefs.node_name.as_bytes());
        hasher.update(prefs.owner_name.as_bytes());
        hasher.update(&entropy);
        let seed = hasher.finalize();
        let ed25519_keypair = Keypair::generate_from_seed(seed.as_bytes());
        let ml_dsa_keypair = MlDsaKeypair::generate(); // отдельный, квантово-устойчивый
        
        // Фрактальный профиль, уникальный как отпечаток пальца
        let fractal_profile = NodeFractalProfile {
            d_f_body: 1.2 + (seed[0] as f64 / 255.0) * 0.6,
            d_f_brain: 1.5 + (seed[1] as f64 / 255.0) * 0.7,
            d_f_soul: 1.3 + (seed[2] as f64 / 255.0) * 0.5,
            alpha_min: 0.5 + (seed[3] as f64 / 255.0) * 0.3,
            alpha_max: 1.2 + (seed[4] as f64 / 255.0) * 0.6,
        };
        
        Self { /* ... */ }
    }
}
```

**Шаг 3: Получение цифрового паспорта и подключение к рою**
Имея ключи, Тамагочи от имени ноды обращается к локальному SPIRE Agent с запросом на выпуск SPIFFE ID. Если SPIRE Agent недоступен, нода переходит в автономный режим. Затем активируется dtn7-rs и eBPF-программы Cilium. Нода пытается обнаружить Beacon через gossip-протокол.

**Шаг 4: Загрузка генома и активация агентов**
Подключившись к Beacon, нода получает начальный пакет знаний (YASA, базовые GDSL-схемы). Получив геном, она активирует пул из 7 TUI-агентов. Тамагочи сообщает Хозяину о готовности: «Я готова. Моя фрактальная размерность 1.64. Можешь давать задания».

### 4. Результат для пользователя и системы

Пользователь (alice или bob_500) получает готовую, уникальную ноду, потратив ровно столько времени, сколько нужно для ответа на три вопроса. Он не думает о ключах, IP-адресах или политиках безопасности. Внутри системы WATERS, тем временем, появляется новый, математически неповторимый фрактальный узел, готовый занять своё место в рое и начать общую эволюцию.

Этот процесс и есть истинное рождение «снежинки» — не ручное конструирование, а самозарождение живого организма из «споры» бинарника при первом контакте с реальностью.

## О едином стандарте Ed25519

Наши текущие ноды и блокчейн Solana уже используют один и тот же стандарт цифровой подписи — Ed25519 (EdDSA на эллиптической кривой Curve25519). В Solana ключевая пара Ed25519 используется напрямую: публичный ключ является адресом кошелька, а секретный ключ — для подписи транзакций. Это означает, что наши ноды технически совместимы с Solana на уровне ключей.

### 🛡️ Проблема квантовой угрозы

Проблема в том, что классический Ed25519, который мы используем, не является квантово-устойчивым. Мощный квантовый компьютер, использующий алгоритм Шора, сможет взломать его за секунды, полностью скомпрометировав все наши ключи.

### 🔮 Что мы можем сделать: Гибридный подход

Решение — использовать гибридную подпись (Ed25519 + PQC). Мы создадим наш Keypair таким образом, чтобы он был на 100% совместим с Solana и при этом защищен от квантовых атак. Вот как это будет работать:

**Генерация:** Мы создаем классический ключ Ed25519. Параллельно из того же источника энтропии (seed) мы генерируем постквантовый (PQC) ключ, например, SLH-DSA (SPHINCS+).

**Идентификация:** Публичный Ed25519-ключ используется как наш основной идентификатор в Solana и P2P-сети libp2p. Это гарантирует полную обратную совместимость.

**Подпись (транзакции):** Для обычных действий в сети Solana мы используем только Ed25519-подпись, чтобы транзакция была принята сетью.

**Подпись (критически важные данные):** Для передачи Знаний, мутаций генома и команд Ясы мы создаем гибридную подпись. Она содержит две подписи: Ed25519 и SLH-DSA. Это обеспечивает квантовую защиту уже сегодня и готовит систему к будущему переходу Solana.

### 📈 Следуя стратегии Solana

Важно, что этот подход полностью соответствует долгосрочной стратегии самого блокчейна Solana. Фонд Solana уже опубликовал план миграции на постквантовую криптографию. Это означает, что через несколько лет гибридная схема станет основной, и мы будем к этому полностью готовы.

### 💻 Как это будет выглядеть в коде

Вот примерный код, как это может быть реализовано в нашем waters-core:

```rust
use ed25519_dalek::{SigningKey, VerifyingKey, Signature};
use slh_dsa::SigningKey as PqcSigningKey; // Крейт для SLH-DSA

pub struct HybridKeypair {
    // Наш основной классический ключ (совместим с Solana)
    pub ed25519_signing_key: SigningKey,
    // Постквантовый ключ для защиты критических данных
    pub slh_dsa_signing_key: PqcSigningKey,
}

impl HybridKeypair {
    pub fn sign_knowledge(&self, data: &[u8]) -> HybridSignature {
        let ed_sig = self.ed25519_signing_key.sign(data);
        let pqc_sig = self.slh_dsa_signing_key.sign(data);
        HybridSignature { ed_sig, pqc_sig }
    }
}

pub struct HybridSignature {
    pub ed_sig: Signature,
    pub pqc_sig: slh_dsa::Signature,
}
```

Эта архитектура позволяет нам:
